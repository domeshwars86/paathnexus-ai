# API specification

## Payment sandbox webhook
`POST /api/v1/webhooks/payments/sandbox` is public and rate-limited. It is disabled unless `PAYMENT_GATEWAY=sandbox` and `PAYMENT_SANDBOX_WEBHOOK_SECRET` is configured. Send `X-PaathNexus-Signature` as the lowercase hex HMAC-SHA256 of the exact raw JSON request body. Invoice `payment.captured` events contain `event_id`, `organization_id`, `invoice_id`, integer `amount_paise`, `method` (`cash`, `bank_transfer`, `upi`, `cheque`, or `other`), and `transaction_reference`. Course `course.payment_captured` events replace `invoice_id` with `course_order_id` and must match the order total exactly. Exact event redeliveries return `duplicate`; changed-body reuse of an event ID returns 409. This is a sandbox ledger simulation only and never initiates a transfer.

`GET /organizations/{organization}/search?q=...` returns up to 20 class, learner, course, task, fee invoice, announcement, and attendance matches for the active workspace. Each result has `id`, `type`, `title`, and `subtitle`; IDs may be UUID strings or integer attendance-session IDs. Course results also match active lesson titles and body text and include the matching lesson title in the result subtitle. Announcement title/body matches follow announcement visibility: members see published notices for all members or their role audience; members with `academic.manage` can also find scheduled and withdrawn notices. Attendance matches class names or exact ISO dates within the same latest-30 session set returned by attendance history, requiring both `attendance.read` and `academic.view`. Queries require 2–80 characters. Teacher, student, and guardian matches use the same active assignment, enrollment, guardian-link, and fee-invoice permission scopes as their workspace views. Student and guardian course/lesson matches are limited to active enrollments. Invoice results include the invoice number, title, and student code; student and guardian invoice results are limited to the student's own invoices or invoices for actively linked learners. Tasks appear only for members with task-read access.

`GET|POST /organizations/{organization}/student/study-plans` lists and creates plans for the linked student profile. Create accepts `title`, future `scheduled_at`, `duration_minutes` (5–240), and optional `course_id` for an actively enrolled course. `POST /organizations/{organization}/student/study-plans/{plan}/complete` completes a planned session once. Plans are private to the student account; the generated OpenAPI contract describes the bounded list, create, and completion payloads.

The API is versioned under `/api/v1`. The generated OpenAPI 3.1 route contract is available in [`openapi.json`](openapi.json). Regenerate it after route changes with `cd api && php artisan openapi:export`; verify it in CI or locally with `php artisan openapi:export --check`. All registered request bodies now have route-specific schemas instead of the generic `JsonObject`; the OpenAPI feature test guards against regression. Some remaining response records and nested nullable/conditional fields still need a complete field-level audit. Refer to this specification for field-level validation, business behavior, and tenant authorization.

## Initial endpoint groups
- `POST /organizations/{organization}/feedback`: any active organization member may submit `category` (`bug`, `idea`, `support`, or `other`) and a 10–5,000 character `message`; email verification is required only when the verification gate is enabled. Requests are limited to five per minute. The record stays in that workspace; no email or push is sent. OpenAPI defines the bounded request and response fields.
- `GET /organizations/{organization}/feedback/mine`: any active workspace member can list up to 100 of their own submissions, status, and manager responses. Other members' submissions are not returned; member-facing response items omit submitter/responder names.
- `GET /organizations/{organization}/feedback`: members with `members.manage` can review the latest 100 workspace submissions with submitter and responder names. OpenAPI keeps these manager-only names in a separate response schema.
- `PATCH /organizations/{organization}/feedback/{feedback}`: members with `members.manage` can update status (`open` or `resolved`) and an optional response of up to 5,000 characters. Omitted responses are preserved. Changed status/replies create or refresh one private in-app notification for the submitter; notification read state is scoped to that member/workspace. Feedback is workspace-scoped; submitters can see the response and status through the `mine` endpoint. Non-managers are denied updates and cross-workspace IDs return 404.
- `GET /organizations/{organization}/roles` lists permission profiles and active admin, educator, teacher, student, and guardian assignments for workspace managers. `POST|PUT|DELETE /organizations/{organization}/roles[/{role}]` create, update, and archive profiles; `POST /organizations/{organization}/roles/{role}/restore` restores an archived profile. `PUT /organizations/{organization}/roles/{role}/members/{user}` assigns a profile to an active member of the matching base role; `DELETE /organizations/{organization}/role-members/{user}` returns that member to standard permissions. Owners cannot be assigned a profile. Profiles must retain their role's core access and may only grant capabilities from that role's configured set. Archiving retains assignments and permissions until restored or explicitly unassigned. OpenAPI represents permission lists as role-specific configured strings and models restore/assignment actions without request bodies.
- `GET /auth/me` returns the authenticated user's profile and active workspaces. `PUT /auth/profile` updates only the current user's display name (`name`, required string, 1–120 characters); email changes are not supported by this endpoint. Both require an authenticated and active account; verification is required when `PAATHNEXUS_REQUIRE_EMAIL_VERIFICATION` is enabled.
- `GET /health`: database-independent liveness response (`status: ok`). `GET /health/ready` probes the configured database and returns `status: ready` with `checks.database: ok`, or a generic `503` `not_ready` response without connection details. Both endpoints are public and reveal no credentials or exception text.
- `GET /catalog/courses?q=...&page=...`: public paginated summaries for active courses explicitly marked public in active workspaces, including `amount_paise`. Returns only opted-in educator profiles assigned to each listed course; it does not return lessons, assignments, student data, or private catalog records.
- `GET /catalog/educators?q=...&page=...`: public paginated educator directory. Results include only active profiles that opted into public display, linked to active user accounts with an active teacher membership in an active workspace. Responses contain the published name, title, biography, and workspace summary; they omit email addresses, user IDs, and employee codes.
- `POST /platform/users/lookup`: allowlisted platform admins may look up one account by exact email. The response is limited to account status, verification and creation timestamps, and workspace membership summaries; it excludes student/teacher profile fields, credentials, and tokens. Successful lookups write a metadata-only platform audit event.
- `POST /catalog/courses/{courseId}/enroll`: authenticated, verified learners can self-enroll only when they hold an active student membership and active linked student profile in the course's active organization, and the course is active, public, and free. The action is idempotent for an existing active enrollment and reactivates a prior ended enrollment. Workspace status is locked and checked in the same transaction to serialize against platform suspension. Paid courses return 402 until checkout is available.
- `POST /catalog/courses/{courseId}/orders`: authenticated linked students can create an order for a paid active public course only while `PAYMENT_GATEWAY=sandbox`; it snapshots the amount in paise, expires after 30 minutes, and reuses the buyer's live pending order. This creates no charge or enrollment.
- `GET /catalog/course-orders/{orderId}`: a buyer can view only their own course order state.
- `GET /catalog/plans`: public active subscription plan descriptions and pricing. This endpoint does not initiate billing.
- `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`. New accounts require signed email verification before login or workspace API access when `PAATHNEXUS_REQUIRE_EMAIL_VERIFICATION` is enabled. The flag defaults to false for `APP_ENV=local` and true otherwise; set it explicitly to true in staging and production.
- `POST /auth/resend-verification`, `GET /auth/verify-email/{id}/{hash}`: rate-limited generic resend response and expiring signed email verification link.
- `POST /auth/forgot-password`, `POST /auth/reset-password`: generic reset-request response, Laravel broker token validation, password policy enforcement, and revocation of all API tokens after a successful reset. Reset email delivery depends on the configured mailer.
- `GET /organizations`, `POST /organizations`, `GET /organizations/{organization}`. Implemented; organization read access is membership-scoped.
- `PUT /organizations/{organization}`: update workspace name, locale, or timezone; owner/admin capability only. Implemented.
- `GET /organizations/{organization}/members`: list active members for member-view capability. Implemented.
- `GET /organizations/{organization}/dashboard`: implemented tenant-scoped counts, latest attendance, recent attendance series, and class roster summary, filtered by the caller's capabilities. Nullable counts indicate unavailable capabilities or an assignment-scoped value that does not apply. The payload includes up to five attendance points, six classes, and six entries for today's schedule. Teacher per-class counts and active-enrollment totals match each whole-class/section assignment rather than combining assignments across classes. The generated OpenAPI contract describes this response shape.
- `GET /organizations/{organization}/student/dashboard`: linked student memberships receive their enrolled active courses and completion, private certificate snapshots earned, published upcoming assignments and own submission state, recent submitted assessment results when allowed, upcoming class timetable entries for their active class enrollments, and an attendance count/rate with five recent attendance records. Study suggestions prioritize unsent assignments, the latest reviewed assessment score below 70% (only when `results.view` is allowed), and unfinished courses. These are transparent rules-based suggestions, not AI-generated evaluations. The generated OpenAPI contract describes the nullable unlinked-profile shape and the nested learner dashboard response.
- `GET /organizations/{organization}/reports/academic`: owners, admins, educators, and assigned teachers require `reports.view`, `academic.view`, and `attendance.read`. They receive organization or assigned-class totals and active-student attendance, course completion, assignment, and assessment summaries. Assignment workload counts published assignments in each student's active enrollments in active courses; submitted/graded counts exclude ended enrollments and inactive courses. Optional `class_id` and `student_id` filters narrow result rows and summary totals. Optional inclusive `from=YYYY-MM-DD` and `to=YYYY-MM-DD` filter attendance sessions, submitted assignments, and completed assessment attempts; course completion and assignment workload remain current-state metrics. Linked teachers receive only assigned classes, learners, and accessible courses; class filters, selected students, and returned class labels are matched to the teacher's specific class/section assignments, including when a student has enrollments in several classes. Inverted date ranges are rejected. The response includes `assignments_assigned`, `assignments_submitted`, and `assignments_graded` in both `summary` and each student row, plus `summary.assessment_score_bands` counts for completed graded attempts in `<60`, `60–74`, `75–89`, and `90%+` ranges, `summary.assessment_trend` (a month-ascending list of `{ month, attempts, average_percent }` grouped by `submitted_at`), `summary.assessment_breakdown` (a list of `{ assessment_id, assessment_title, course_id, course_title, attempts, average_percent }`), and `summary.assessment_course_summary` (a list of `{ course_id, course_title, attempts, average_percent }`). Score-band, trend, per-assessment, and course results share the same tenant, teacher-course, learner, status, and date filters as assessment averages; trend and per-group averages are weighted by attempts. The generated OpenAPI contract describes the response envelope and field types.
- `POST /organizations/{organization}/ai/tutor`: active members with authorized course access may ask the configured educational tutor a question and optionally reference an authorized course lesson; teachers may attach only courses they created or were assigned to teach, even when they have `courses.manage`. The API enforces tenant/content permissions, common PII-pattern checks (including labeled passport and voter-ID values), shared daily AI quotas, rate limits, and token metering.
- `POST /organizations/{organization}/ai/teacher-assistant`: members with effective `courses.manage` can request editable teaching drafts (`lesson_plan`, `course_outline`, `learning_objectives`, `mcqs`, `practice_exercises`, `homework_questions`, `revision_notes`, or `rubric`) in English (`en`) or Hindi (`hi`). `topic` is required (3–160 characters), `grade_level` optional (max 80), and `instructions` optional (max 1,000). Drafts require human review, are not saved or published, and requests use the same quotas, throttles, PII checks, and metadata-only usage ledger as the tutor.
- `GET|POST /organizations/{organization}/invitations`, `DELETE /organizations/{organization}/invitations/{invitation}`: members managers list invitations, create seven-day teacher/student/guardian invitations, and revoke pending invitations. Creation returns a one-time plaintext token for manual link sharing; only its hash is stored.
- `POST /invitations/accept`: an authenticated user accepts a pending invite when the account email matches. `POST /auth/register-invitation` creates an account for a not-yet-registered invited email and accepts the invitation atomically. Tokens are single-use, expire, and cannot grant owner/admin roles.
- `GET|POST /organizations/{organization}/attendance-sessions`. Lists the latest 30 scoped sessions and supports legacy aggregate snapshots. The generated OpenAPI contract describes session and attendance-record response shapes.
- `POST /organizations/{organization}/classes/{class}/attendance-sessions`: record a full active class roster or a selected section roster for today; repeated submissions update that class/section/day session. Teachers must have the matching whole-class or section assignment. Each active roster member must appear exactly once. The OpenAPI request schema lists allowed record status values.
- `GET|POST /organizations/{organization}/classes`, `GET|POST /organizations/{organization}/students`, and `POST /organizations/{organization}/classes/{class}/enrollments`. Implemented with tenant membership and academic capability checks. Teacher class lists return only students enrolled in each class/section assigned to that teacher. Roster, student, enrollment, and request shapes are described in OpenAPI.
- `GET|POST /organizations/{organization}/academic-years`, `POST /organizations/{organization}/academic-years/{year}/activate`, `GET /organizations/{organization}/sections`, `POST /organizations/{organization}/classes/{class}/sections`, `GET|POST /organizations/{organization}/timetable-entries`, and `PUT /organizations/{organization}/timetable-entries/{entry}`. Creation and updates require academic management permission, tenant-owned references, and collision checks for classes and teachers; updates exclude the entry being edited. Academic-year, section, and timetable request/response shapes are described in the generated OpenAPI contract. Timetable reads accept optional `academic_year_id` and `weekday` filters.
- `GET|POST /organizations/{organization}/schedule-exceptions`, `PUT /organizations/{organization}/schedule-exceptions/{exception}`, and `POST /organizations/{organization}/schedule-exceptions/{exception}/cancel`: view, create, edit the title/notes of an active exception, or cancel tenant-scoped closures, class/section cancellations, and one-day extra lessons. Dates and schedule scope are fixed after creation. Dates must fall within the selected academic year; only one active closure is allowed per date; extra lessons validate subject offerings and class/teacher conflicts. Cancellation remains in the history with its actor and timestamp.
- `GET|POST /organizations/{organization}/live-sessions`, `PUT /organizations/{organization}/live-sessions/{session}`, and `POST /organizations/{organization}/live-sessions/{session}/join`: list scoped live meetings, schedule a class/section or course session, transition its status, or obtain an external meeting URL during the authorized access window. Learner lists and direct meeting access require an active enrolled course; changing a course to draft hides its session from learners. Session lists never contain meeting URLs.
- `GET /organizations/{organization}/live-sessions/{session}/roster` and `POST /organizations/{organization}/live-sessions/{session}/attendance`: authorized instructors review the active session roster and record complete attendance into the standard attendance ledger. Provider-verified presence requires a conferencing webhook and is not currently available.
- `GET|POST /organizations/{organization}/subjects` and `GET|POST /organizations/{organization}/teachers`. Implemented with workspace-unique subject codes/names and teacher employee codes. Subject and teacher profile request/response shapes are described in OpenAPI; teacher status can be active or inactive, while list results contain active profiles only.
- `GET /organizations/{organization}/teachers/member-candidates` and `PUT /organizations/{organization}/teachers/{teacher}/member`: list active, unlinked teacher members and link/unlink a profile. Academic management capability required; candidate, request, and profile response shapes are described in OpenAPI.
- `PUT /organizations/{organization}/teachers/{teacher}/public-profile`: the linked teacher can set nullable `public_title` (max 120) and `public_bio` (max 1,200), and must provide `is_public`. The response includes the updated profile and public fields; other members receive null public fields in teacher listings.
- `GET|POST /organizations/{organization}/classes/{class}/subject-offerings` and `DELETE /organizations/{organization}/classes/{class}/subject-offerings/{offering}`: list, add, or end a subject offering for a class or section in an academic year. `GET /organizations/{organization}/classes/{class}/teachers`, `POST` on the same path, teacher-assignment history, and `PUT|DELETE .../teachers/{assignment}` manage current class-teacher assignments and review their event history. The generated OpenAPI contract describes these payloads and academic-year filters.
- `GET|POST /organizations/{organization}/classes/{class}/teachers`: list or assign a teacher to a whole class or section for an academic year. Tenant ownership and duplicates are checked; academic view/manage capabilities apply.
- `PUT|DELETE /organizations/{organization}/classes/{class}/teachers/{assignment}` and `GET /organizations/{organization}/classes/{class}/teacher-assignment-history`: change/end a class teacher assignment and review its assignment/reassignment/removal events.
- `GET|POST /organizations/{organization}/classes/{class}/subject-offerings` and `DELETE /organizations/{organization}/classes/{class}/subject-offerings/{offering}`: list, offer, and end subjects for a class or section in an academic year.
- `GET|POST /organizations/{organization}/courses`, `GET|POST /organizations/{organization}/courses/{course}/lessons`, and `GET|POST /organizations/{organization}/courses/{course}/enrollments`: manage courses, lesson content, and learner enrollment. Course create/update accepts `price_paise` as an integer INR paise amount (0 means free); learner enrollment through the public catalog is blocked for nonzero prices until payment checkout exists. Teachers can manage courses they created or are assigned to teach; their learner records are limited to students in assigned whole classes or sections. Course and lesson authoring response shapes are represented in the generated OpenAPI contract.
- `GET /organizations/{organization}/course-instructors` and `PUT /organizations/{organization}/courses/{course}/instructors`: owners, administrators, or educators list active teacher candidates and replace the assigned teacher set. Only active teacher memberships in the same workspace are accepted. Candidate, update request, and course response shapes are represented in OpenAPI.
- `GET|POST /organizations/{organization}/courses/{course}/enrollments`: managers list active enrolled learners or enroll an active learner profile. Teachers remain limited to their assigned learner scope. The generated OpenAPI contract distinguishes the enrollment list and create response.
- `PUT /organizations/{organization}/courses/{course}` and `PUT /organizations/{organization}/courses/{course}/lessons/{lesson}`: course managers update course content/visibility or edit/archive/restore a lesson. Draft courses and archived lessons are not delivered to students; related progress records are retained.
- `GET /organizations/{organization}/courses/{course}/progress` and `PUT /organizations/{organization}/courses/{course}/lessons/{lesson}/progress`: review course completion and save started/completed status. Learners can only change their own linked profile; teachers can read or record progress only for learners in their active class/section assignments, while other course managers can record progress for enrolled learners. The generated OpenAPI contract describes lesson prerequisites, per-learner progress rows, and progress-update requests.
- `GET|POST /organizations/{organization}/courses/{course}/assignments`, `POST /organizations/{organization}/assignments/{assignment}/submissions`, `GET /organizations/{organization}/courses/{course}/assignments/{assignment}/submissions`, and `PUT /organizations/{organization}/courses/{course}/assignments/{assignment}/submissions/{submission}/grade`: publish assignments, submit written work, review submissions, and grade them. The generated OpenAPI contract describes their response envelopes and JSON/multipart request shapes; grading scores are bounded by the selected assignment's maximum at runtime.
- `POST /organizations/{organization}/courses/{course}/assignments/{assignment}/attachments`: managers attach up to five resource files. `GET /organizations/{organization}/courses/{course}/assignments/{assignment}/attachments/{attachment}` downloads a resource for an enrolled learner or authorized course manager, or a submission attachment for its learner and scoped educators only.
- `GET|POST /organizations/{organization}/courses/{course}/questions` and `GET|POST /organizations/{organization}/courses/{course}/assessments`: manage single-choice, multiple-select, and short-answer question banks, including topic/difficulty metadata, and publish multi-question quizzes with per-question points, time limits, attempt limits, optional ISO-8601 `opens_at`/`closes_at` availability windows, per-attempt question-order randomization, and optional random sampling from a larger selected pool. Both window values are nullable; if both are supplied, `closes_at` must be later than `opens_at`. Learners see scheduled times and cannot start before `opens_at` or at/after `closes_at`; new attempts require an active course, while an already-started in-progress attempt can be resumed/submitted and a learner's own historical result remains readable after a course becomes draft. `randomized_question_count` is null to include the full pool or a positive count up to its size. Correct options are returned only to members with `assessments.manage`. CSV import currently supports objective question types. The generated OpenAPI contract describes assessment summaries and core attempt, analytics, and student-result responses.
- Assessment authoring, answer-key question-bank access, analytics, grading, and grade exports require the dedicated `assessments.manage` capability. `courses.manage` alone allows reading published assessment summaries but does not grant answer-key or grading access. Teachers can reach created/assigned courses with `courses.view`; lesson and published-assignment reads remain scoped through the teacher course scope.
- The OpenAPI contract defines question creation limits (prompt 5,000 characters, difficulty 1–5, objective options 2–8, and short-answer rubrics 2–10 criteria with weights totaling 100), assessment creation limits (1–100 unique questions, 1–10 attempts, and 1–360 minute duration), and discriminated request alternatives for objective versus short-answer submissions and rubric versus manual-point grading. Question imports use required `multipart/form-data` field `file`, accept CSV files up to 1 MiB, and process at most 100 question rows; question records, preview rows, import success, and import validation-failure responses are also described. Dynamic assessment point limits, exact rubric membership, and cross-field rules are additionally enforced at runtime.
- `POST /organizations/{organization}/courses/{course}/questions/import/preview` and `POST /organizations/{organization}/courses/{course}/questions/import`: members with `assessments.manage` can preview and import CSV question rows. Files are limited to 1 MB and 100 questions; every row must validate before the transaction writes any questions. The CSV header uses `prompt,type,difficulty,topic` and two to eight numbered `option_N,option_N_correct` pairs; correctness accepts `true/false`, `yes/no`, or `1/0`.
- `POST /organizations/{organization}/assessments/{assessment}/attempts`, `PUT /organizations/{organization}/assessments/{assessment}/attempts/{attempt}/answers/{question}`, `POST /organizations/{organization}/assessments/{assessment}/attempts/{attempt}/submit`, and `GET /organizations/{organization}/courses/{course}/assessments/{assessment}/attempts`: learner quiz attempts, persisted sample and stable resume order, answer saving restricted to sampled questions, objective scoring, and pending review for written responses. Learners may only access their own enrolled-course attempts.
- `GET /organizations/{organization}/courses/{course}/assessments/{assessment}/analytics` and `GET /organizations/{organization}/courses/{course}/assessments/{assessment}/attempts`: optional `from=YYYY-MM-DD`, `to=YYYY-MM-DD`, and `student_id` filters narrow attempt counts, averages, question accuracy, and review lists. Teacher figures remain restricted to assigned students; analytics responses contain no learner identifiers.
- `GET /organizations/{organization}/courses/{course}/assessments/{assessment}/attempts/{attempt}/review`: members with `assessments.manage` review completed-attempt answers and correct options. Teacher access is restricted to assigned students; in-progress attempts are not reviewable.
- `GET /organizations/{organization}/courses/{course}/assessments/{assessment}/grades/export`: members with `assessments.manage` download a filtered grade CSV. Teacher rows remain limited to assigned students, and text cells are neutralized against spreadsheet formulas.
- `PUT /organizations/{organization}/courses/{course}/assessments/{assessment}/attempts/{attempt}/answers/{question}/grade`: members with `assessments.manage` award up to the question's configured points to a submitted short answer and optionally save feedback. Attempts remain pending until all written responses have been reviewed.
- `GET /organizations/{organization}/assessments/{assessment}/attempts/{attempt}/result`: learners read their own submitted answers, awarded points, pending state, and released educator feedback. Correct options are not included.
- `GET /organizations/{organization}/guardian-candidates`, `GET|POST /organizations/{organization}/guardian-student-links`, and `DELETE /organizations/{organization}/guardian-student-links/{link}`: academic managers list active guardian memberships, link a guardian to a student, and revoke access. Create may return 201 for a new link or 200 when restoring an existing link. The generated OpenAPI contract describes candidate, link, and request bodies.
- `GET /organizations/{organization}/guardian/students`: a guardian reads only explicitly linked students’ attendance, lesson completion, published homework status, and completed assessment summaries. Homework and learning are returned only when `courses.view` is granted; results require `results.view`; published exams scheduled to open in the future require both. Homework shows up to eight published assignments from active course enrollments that are not overdue, with due date and submitted/graded/not-submitted status; scores and submission content are not returned. The first-party portal can export the summary to CSV. Projections are omitted when the guardian lacks their corresponding capability; the OpenAPI child schema keeps those fields optional.
- `POST /organizations/{organization}/ai/tutor`: ask the configured AI tutor, optionally with a course and lesson context. Active course viewers/managers only; teachers are limited to courses they created or were assigned, while students need active enrollment. Rate limited, daily quota tracked, prompt text not persisted, and provider failures return an unavailable response. Requires `AI_API_KEY` and `AI_MODEL` configuration.
- `POST /organizations/{organization}/ai/teacher-assistant`: course managers request an unsaved teaching draft using `draft_type`, `topic`, optional `grade_level` and `instructions`, and `language` (`en` or `hi`). The configured provider, workspace quota, and personal-data filter apply; the response marks `human_review_required=true`. OpenAPI describes the request, answer/draft envelopes, and token usage counters.
- `GET|POST /organizations/{organization}/announcements`, `PATCH /organizations/{organization}/announcements/{announcement}`, `POST /organizations/{organization}/announcements/{announcement}/withdraw`, `POST /organizations/{organization}/announcements/{announcement}/restore`, `GET /organizations/{organization}/notifications`, and `POST /organizations/{organization}/notifications/{notification}/read`: publish immediate or future audience-scoped announcements; scheduled items are visible only to academic managers until due, and the audience is fixed when created; academic managers may correct title/body without changing audience; withdraw or restore an announcement while retaining its previous published/scheduled state and notification rows; list visible announcements and private in-app notifications, including feedback updates; and mark a recipient's own notification as read. Notification visibility and unread counts are re-evaluated against the member's current role, and marking a notification outside that role's audience returns 404. Withdrawn items and their notifications are hidden from members until restored. Active audience members receive an in-app notification when the item publishes. OpenAPI distinguishes announcement and feedback notification variants, includes the unread total, and models the read action without a request body. The `announcements:publish-scheduled` command runs every minute through Laravel's scheduler.
- `GET /organizations/{organization}/fee-invoices?page=1&per_page=25&from=YYYY-MM-DD&to=YYYY-MM-DD` returns role-scoped invoice rows and `meta` pagination fields (`current_page`, `last_page`, `per_page`, `total`). Page size is 1–100; `from`/`to` are inclusive invoice issue dates in the workspace timezone, and inverted ranges are rejected. Tenant and learner/guardian scopes are applied before pagination. `POST /organizations/{organization}/fee-invoices` issues INR invoices; `GET /organizations/{organization}/fee-invoices/summary` is limited to members with `academic.manage` and returns all-time invoice, paid, outstanding, and overdue counts and amounts in paise for that workspace. Students and linked guardians can read their balances and receipt references but cannot view workspace totals. `POST /organizations/{organization}/fee-invoices/{invoice}/void` and `/payments` let authorized staff void unpaid invoices and record reconciled offline receipts with an idempotency key. Overpayments are rejected and paid/partially-paid invoices cannot be voided. No gateway transfer is initiated. OpenAPI specifies the decimal rupee request fields and paise integer responses.
- `GET /organizations/{organization}/fee-invoices/collections?from=YYYY-MM-DD&to=YYYY-MM-DD&page=1&per_page=25` requires `academic.manage` and returns only reconciled payments received in the inclusive workspace-timezone date range, with aggregate `payment_count` and `collected_paise` plus paginated receipt, invoice, and learner summaries. Page size is 1–100; both dates are required and inverted ranges are rejected. The endpoint scopes by organization before totals and pagination. It does not initiate or verify gateway transfers; the generated OpenAPI contract describes the date filters, summary, pagination, and receipt rows.
- `GET /organizations/{organization}/subscription` and `POST /organizations/{organization}/subscription/requests`: view current plan/entitlements and request a plan change (workspace owner only).
- `GET|POST /platform/plans`, `PUT /platform/plans/{plan}`, `GET /platform/subscription-requests`, and `POST /platform/subscription-requests/{organization}/resolve`: manage plans and review changes. Platform routes require an authenticated email in `PAATHNEXUS_PLATFORM_ADMIN_EMAILS`; approving a paid or custom-priced plan requires a verified reference and writes an audit event.
- `GET /platform/organizations?q=...&status=...&page=...` and `PUT /platform/organizations/{organizationId}/status`: allowlisted platform administrators search a paginated organization directory with aggregate active usage counts and subscription summary, then suspend or reactivate a workspace. Responses exclude member contact details. Status changes accept `active` or `suspended`, an optional audit note, and write a platform audit event; suspended workspaces cannot be accessed by tenant members.
- `GET /platform/usage`: returns platform-wide organization totals and active membership, student, course, and subscription counts. Requires the configured platform-admin email allowlist; usage counts exclude suspended workspaces.
- `GET /platform/usage/history?days=90`: returns daily aggregate snapshots for the requested 7–365 day window; requires the configured platform-admin email allowlist. Snapshots contain counts only. The scheduled `platform:capture-usage-snapshot` command writes one idempotent row per UTC date; historical records are not backfilled.
- `GET /platform/audit-logs?event=...&subject_id=...&page=...`: allowlisted platform administrators list the latest 25 audit records or filter by exact event and subject ID. The response includes actor ID, event, subject type/ID, and timestamp; it excludes raw details and free-form notes.
- `GET /platform/feature-flags` and `PUT /platform/feature-flags/{flag}`: allowlisted platform administrators view and update configured global feature flags. Updates persist only when the value changes and create a metadata-only platform audit entry. The AI tutor and teacher-assistant endpoints enforce their respective flags; unknown keys return 404. Flags currently apply globally rather than per workspace.
- `GET /organizations/{organization}/students/member-candidates` and `PUT /organizations/{organization}/students/{student}/member`: link a learner profile to one active student membership in the same workspace.
- `GET|POST /organizations/{organization}/tasks`, `PATCH /organizations/{organization}/tasks/{task}`, `POST /organizations/{organization}/tasks/{task}/complete|archive|restore`, and `GET /organizations/{organization}/task-assignees`. Task changes are capability-gated and tenant-scoped; the assignee candidate list contains only active staff memberships.

## API rules
- JSON requests and responses; consistent validation errors and pagination envelope.
- Authenticate with Sanctum for the first-party SPA, protect state-changing requests against CSRF, and rate-limit authentication and AI endpoints.
- Resolve tenant access from authenticated membership and policy checks. Validate nested resource ownership on every write.
- Use idempotency keys for payment/webhook operations when those modules are introduced.
- Never return private fields or cross-tenant existence details.

Registration fields: `name`, `email`, `password`, `password_confirmation`, `organization_name`, `organization_type`. Passwords require 12+ characters including letters, mixed case, and numbers. Auth endpoints are limited to 6 requests per minute; verification links expire after 60 minutes. Sanctum bearer tokens expire after 60 minutes by default (`SANCTUM_TOKEN_EXPIRATION`). The local mailer defaults to `log`, so configure an approved SMTP or other mail transport for inbox delivery of verification and password reset links.

Initial capabilities are configured per membership role. Only owners/admins can update organization settings or list member contact details; non-members receive 404, while members without the required capability receive 403.

## Custom permission profiles

Workspace members with `members.manage` can use `GET|POST /organizations/{organization}/roles`, `PUT|DELETE /organizations/{organization}/roles/{role}`, `POST /organizations/{organization}/roles/{role}/restore`, `PUT /organizations/{organization}/roles/{role}/members/{user}`, and `DELETE /organizations/{organization}/role-members/{user}`. Profiles have an immutable `base_role` of `admin`, `teacher`, `student`, `guardian`, or `educator`; owners are excluded. Their `permissions` must be a subset of that base role's configured capabilities. Teacher profiles must retain `organization.view`, `academic.view`, `attendance.read`, and `courses.view`; student profiles must retain `organization.view`, `courses.view`, and `results.view`; guardian profiles must retain `organization.view` and `students.view`; admin and educator profiles must retain `organization.view`. Educator custom profiles use explicit configured capabilities instead of the default wildcard. Assignment requires the active membership to match the profile base role. Archived profiles cannot be newly assigned and archiving retains existing assignments until restore or explicit unassignment. API responses expose effective organization permissions to drive UI visibility; server policy checks remain authoritative. Student `attendance.read` controls the attendance projection, `fees.view` controls invoice listing, and `assessments.take` controls attempt creation and updates. Guardian `attendance.read`, `courses.view`, and `results.view` independently control which linked-student summary sections are queried and returned.

Workspace search is tenant-scoped and role-scoped. Guardian course results require `courses.view` even when the guardian has linked students; linked-child access alone does not grant course search visibility. Invoice results require `fees.view`; student and guardian invoice matches are limited to their own or actively linked learner profiles. Announcement results use the same role audience and publication-state filters as the announcement index. Attendance results use the same teacher assignment scope as attendance history.

Task creation accepts `title` (required, max 160 characters), `description` (optional, max 2000), `due_at` (optional date), and `assigned_to` (optional active staff member ID in the same workspace). `PATCH /organizations/{organization}/tasks/{task}` accepts one or more of those fields; explicit `null` clears the description, due date, or assignee. `GET /organizations/{organization}/task-assignees` returns active owners, admins, educators, and teachers without email addresses. Task status is `pending` or `completed`; completion records `completed_at`. Archive and restore set or clear `archived_at` while retaining the task. Archived tasks remain in the manager task list's Archived filter and are excluded from dashboard pending counts and workspace search. They must be restored before editing or completing. Active owners, admins, educators, and teachers can view and manage tasks within their organization. Updates are scoped through the organization relation and return 404 for a task owned by another workspace.

Legacy attendance snapshot creation accepts `class_name` and `attendance_rate`. Student-level attendance accepts a `records` array of `{student_id, status}` values with status `present`, `absent`, `late`, or `excused`. Each active enrollment must appear once; the server calculates the rate and assigns the date using the organization timezone. Repeated submissions update the same daily class session. Active members with `attendance.read` can list recent sessions; members with `attendance.write` can submit marks. Class and student creation and enrollment require `academic.manage`; teachers can read classes and rosters.

Class creation accepts a unique workspace `name` plus optional `grade` and `section`. Student creation accepts a workspace-unique `student_code` and `name`. Class enrollment accepts `student_id` plus optional `section_id`; the API verifies the student, class, and selected section belong to the same active workspace and class.

Academic years accept `name`, `starts_on`, `ends_on`, and optional `status` (`planned`, `active`, `completed`). Section names are unique within a class. Subjects accept `code` and `name`; teacher profiles accept `employee_code` and `name`. Timetable entries accept academic year, class, optional section, catalog `subject_id`, optional `teacher_profile_id`, ISO weekday (Monday=1), start/end times, and optional room. The dashboard returns today's entries for the active year using the organization's timezone. Legacy free-text subjects remain accepted for existing clients.

Schedule exception creation accepts `academic_year_id`, `exception_date`, `type` (`closure`, `cancel`, or `extra`), and `title`; optional notes are limited to 2,000 characters. Cancel exceptions require `class_id`, may identify a `section_id` and `timetable_entry_id`, and do not accept subject/teacher/time/room fields. Closures do not accept class, section, timetable, subject, teacher, time, or room fields. Extra lessons require class, subject, start and end time, and may include section, teacher, and room (up to 80 characters); end time must be after start. The list optionally filters by `academic_year_id`, defaults to the active year, and is capped at 200 records. The generated OpenAPI schemas describe the request, nullable response fields, and cancellation timestamp.

Live-session creation requires `title`, `starts_at`, `ends_at`, `meeting_url`, and exactly one of `class_id` or `course_id`; section and description are optional. Start time must be in the future, end must follow start, and the meeting URL must use HTTPS. The session response omits that URL. Updates require a status transition (`scheduled` to `live` or `cancelled`; `live` to `completed` or `cancelled`); a nullable HTTPS `recording_url` may be supplied only while completing. Join requests return the meeting URL and end time only during the authorized access window and, for course audiences, while the course is active. Roster rows contain learner ID, name, and nullable student code. Attendance requests require distinct `{student_id, status}` records (`present`, `absent`, `late`, or `excused`) for every active learner in the session audience; attendance rate counts present and late records.

Teacher profile linking accepts nullable `user_id`; a linked user must be an active teacher membership in the same organization, and each member may link to at most one profile. Class teacher assignment accepts `teacher_profile_id`, `academic_year_id`, and optional `section_id`; omitting the section assigns the teacher to the whole class.

Linked teachers can update only their own active profile with `PUT /organizations/{organization}/teachers/{teacher}/public-profile`, sending `public_title`, `public_bio`, and required `is_public`. The catalog exposes those fields only when the profile owner opted in and is assigned to that public course.

Courses accept a workspace-unique `code`, `title`, optional description, academic year, and subject. Lessons accept title, content, optional external video/document resources, and an optional set of earlier active prerequisite lesson IDs; resource URLs must use HTTPS and lessons receive an ordered position. Course enrollment accepts an active `student_id`; duplicate active enrollment is rejected. Lesson progress status is `started` or `completed`; completion timestamps are recorded and course progress returns completed/total lesson counts and a percentage. Student course reads require an active linked student profile and enrollment. Teacher progress writes require the target to be both actively enrolled and in the teacher's current class/section assignments; completing the last active lesson issues the learner's private completion snapshot. Progress writes are rejected until all lesson prerequisites are complete.

Assignments accept title, optional instructions, optional lesson link, optional due date, maximum points, and draft/published status. Student submissions can include text and up to five files and require active course enrollment; due dates are enforced. Submissions can be resubmitted, which clears the prior grade. Course managers can assign a score no greater than the assignment maximum and optional feedback; teachers can list and grade only submissions from learners within their active class/section assignments. Out-of-scope grade mutations return 404. Learners only receive their own submission and grade. Attachments allow PDF, DOC/DOCX, PNG/JPG/JPEG, and TXT up to 10 MB each; the default private local disk is suitable for development, while deployment needs a persistent private filesystem disk.

Subject offerings accept `academic_year_id`, `subject_id`, and optional `section_id`. If a class has active offerings for a year, timetable entries for that class must use a subject offered to the whole class or the selected section. Ended offerings and assignments remain in the database; teacher assignment history records the actor and old/new teacher profiles.

Announcement, task, subscription, plan, platform directory/usage, assessment answer/review/export, public checkout, payment webhook, health, verification redirect, and private attachment endpoints now have route-specific OpenAPI success response schemas. The contract distinguishes pending versus active subscription changes, readiness failures, CSV and binary downloads, sandbox payment duplicates, and nullable answer/plan fields. Learner dashboard assessment results constrain non-null scores to nonnegative values and constrain `review_status` to `not_required`, `pending`, or `reviewed`, while homework `submission_status` is `submitted`, `graded`, or null; workspace and learner schedule subjects are required text. Subscription-plan audiences, billing intervals, public course organization types, and platform subscription states list their API-validated values. A complete route-by-route audit for conditional and nullable fields remains part of release verification.
