# Security baseline

## Current implementation
Teacher-initiated lesson progress writes require the target learner to be currently assigned to the teacher's active whole-class or section scope, even when the course enrollment is active. Out-of-scope progress requests return 404 before a progress row or completion certificate can be created.

The overview counts, attendance trend, timetable, learning workflows, guardian summaries, academic reports, invitations, and AI tutor and teacher-assistant request flows are backed by workspace data. Teacher class, roster, attendance, timetable, report, and course learner reads use active whole-class or section assignments for the active year; teachers manage courses they created or were assigned to teach. Legacy classless attendance snapshots are visible only to their recorder. Public catalog responses include only courses that an educator explicitly marked public, and never include lesson content. Password reset responses do not reveal whether an email is registered; broker tokens are one-use and successful reset revokes existing API tokens. When PAATHNEXUS_REQUIRE_EMAIL_VERIFICATION is enabled, new accounts must verify their email before sign-in or workspace access; verification links are signed and expire, and resend responses do not disclose account existence. The setting defaults to disabled only for APP_ENV=local and enabled otherwise; set it explicitly to true in staging and production. Local email delivery uses the log mailer until a real transport is configured. AI generation is available only after configuring an approved provider key and model. AI tutor requests require course access and teacher-assistant requests require `courses.manage`; both enforce shared user, organization, and plan limits, rate limits, common contact/identity pattern checks, and metadata-only usage logging. The tutor may retrieve one specifically authorized lesson and redacts common patterns in lesson text. Teaching drafts remain unsaved and require human review. The PII patterns are incomplete and provider retention has not been reviewed; do not send real learner data until those checks and institutional consent are complete. Academic and attendance routes verify active membership and capabilities on every request; composite foreign keys protect tenant links. Tenant-scoped admin, educator, teacher, student, and guardian permission profiles can only narrow configured base-role capabilities and are checked server-side; owners cannot be assigned a profile. Custom educator permissions use an explicit catalog instead of the default wildcard, and profiles preserve each membership's original data scope. Invitation tokens are hashed, email-bound, role-limited, expiring, and single-use. Platform plan administration uses an explicit email allowlist and records plan/subscription decisions in a platform audit table. Fee payment entries are manual records of externally reconciled funds; they do not invoke a gateway. General activity audit coverage is still incomplete. Student names, teacher names, and attendance are sensitive data: use test data in development and complete privacy, access, retention, and audit controls before production use. Sanctum bearer tokens expire after 60 minutes by default and the frontend keeps them in tab-scoped session storage. HttpOnly cookie-based SPA sessions are preferred before production.
Live meeting links are withheld from listings and returned only through an audience-scoped join request within the scheduled access window. Join logs record a link request, not verified provider attendance. Recordings are returned only after a session is marked completed. Configure provider-side access, retention, and webhook signatures before treating attendance as verified.
The payment sandbox webhook is disabled unless explicitly configured, requires an HMAC-SHA256 signature over the exact raw body, and stores only the body digest and event outcome for replay protection. Sandbox events are synthetic ledger entries and do not prove real funds were transferred. Keep the webhook secret in a local/deployment secret store and never place it in source control or logs.
Workspace search reuses active membership checks and filters teacher records through assigned classes/courses, learner records through the linked student profile/enrollment, and guardian records through active guardian links. Search results return names and identifiers needed to locate records, not full profiles. Assessment authoring, answer keys, grading, and analytics require `assessments.manage` independently of course-edit rights; teachers remain restricted to courses they created or were assigned. Scheduled assessment times are enforced server-side; guardian upcoming-exam projections are limited to linked learners' active course enrollments and require both course-view and results-view capabilities.

## Required before real data
- Laravel authentication with secure password hashing, email verification, session security, CSRF protection, login throttling, and account recovery.
- Server-side organization membership checks and policies on every tenant-owned request; cross-tenant negative tests.
- Least-privilege roles, auditable admin actions, secure invitations, and session revocation.
- Encrypt transport and sensitive data at rest; keep secrets in deployment secret stores; redact logs and errors.
- Validate file type, size, ownership, and malware scanning before serving uploads through signed URLs.
- Configure and verify payment-provider signature validation, reconciliation, refunds, and accounting controls before using any online payment flow; the current ledger only records payments verified elsewhere.
- Consent and retention rules appropriate to minors and applicable Indian privacy requirements before production collection.
- Rate limits, quotas, safety policies, and authorized-content checks for AI features.
- AI PII checks include labeled passport and voter-ID values alongside common contact and identity patterns; the patterns remain incomplete and do not replace consent, retention, and privacy controls.
- Service worker caches only the application shell and built assets; API paths are network-only to avoid caching private learner responses.
- The synthetic demo seeder is opt-in, requires `APP_ENV=local`, and reads its shared local-only password from ignored `api/.env`. It is idempotent and creates only fictional records; never enable it in staging or production.
- Teacher academic, attendance, timetable, dashboard, report, and course learner data are restricted to active whole-class or section assignments for the active academic year. Section enrollment is tenant- and class-constrained with composite foreign keys.
- Dependency scanning, backups, restoration and rollback exercises before release.

Never seed private or real learner information. Synthetic demo fixtures must be visibly labeled.
